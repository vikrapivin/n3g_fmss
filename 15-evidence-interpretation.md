# Chapter 15 — Evidence interpretation

Summary: What the outcomes of [chapter 14](14-evidence.md) are taken to show, by topic. Every statement cites its evidence and carries an evidence class (device, observed, inferred or open).

Every statement in this chapter cites evidence entries (`D-<experiment>-<device run>` for device outcomes, device runs as listed in [chapter 13, section 13.2](13-experiments.md#132-device-runs); `RE-<n>` for reverse-engineering outcomes) and carries one of the evidence classes of [chapter 1, section 1.1](01-overview.md#11-evidence-classes):

- **Device**: a fact measured on a unit.
- **Observed**: seen in the original programs or in the original CPU driver.
- **Inferred**: an interpretation of observed use or of measurements.
- **Open**: not settled.

The experiments themselves are described in [chapter 13](13-experiments.md); the finding numbers refer to [chapter 18](18-ledger.md).

## 15.1 Instruction set and registers

- **Device.** The register file is r0..r7 at `0xc18 + 4n`, with `SEQ_RESULT` (`0xc30`) being r6; a CPU write before a start sets the register's starting value; a start keeps the register contents; and a sequencer reset clears the registers (finding 38). Evidence: [`regmap`, device run 1](14-evidence.md#1421-regmap-run-1), [`regmap`, device run 6](14-evidence.md#14228-regmap-run-6), [`regmap`, device run 7](14-evidence.md#14233-regmap-run-7), [`control`, device run 1](14-evidence.md#1426-control-run-1), [`control`, device run 2](14-evidence.md#14212-control-run-2), [`control`, device run 3](14-evidence.md#14218-control-run-3).
- **Device.** A two-instruction loop takes about 216 ns per instruction (873 us for 2 000 iterations and 8 657 us for 20 000 iterations). Evidence: [`clock`](14-evidence.md#1422-clock-run-1).
- **Device.** Instruction time is set by the fetch of the 8-byte instruction: 217 ns from SDRAM and 138 ns from internal SRAM; a register-window access adds 35..37 ns; `ldi` adds 170 ns (SDRAM) or 218 ns (SRAM); and `sti` adds 186 ns (SDRAM) or 120 ns (SRAM). Evidence: [`opcost`](14-evidence.md#14262-opcost-run-15), [`optime`](14-evidence.md#14244-optime-run-11).
- **Device.** ALU edge cases: `shr` is a logical shift; a shift count of 32 or more gives 0 (whether the count is an immediate or a register); `add` and `sub` wrap at 32 bits; an immediate of 0 selects the two-operand (register) form; and `ld` applies its mask by AND. Evidence: [`alu`, device run 1](14-evidence.md#1423-alu-run-1), [`alu`, device run 2](14-evidence.md#14210-alu-run-2), [`alu`, device run 3](14-evidence.md#14216-alu-run-3), [`holdout`, device run 9](14-evidence.md#14238-holdout-run-9), [`holdout`, device run 10](14-evidence.md#14239-holdout-run-10).
- **Inferred.** The ALU operand rule (when the immediate is non-zero, the source register is in the `arg` field; when the immediate is zero, the instruction uses the register form) is the rule that holds in every use in the original programs; an immediate of 0 therefore has no encoding (finding 2). Evidence: [RE-4](14-evidence.md#1434-re-4-instruction-encoding-and-opcode-set-used-by-the-programs). The device test confirms the behaviour of both forms ([`alu`, device run 1](14-evidence.md#1423-alu-run-1), [`alu`, device run 2](14-evidence.md#14210-alu-run-2), [`alu`, device run 3](14-evidence.md#14216-alu-run-3)).
- **Device.** `ldi`/`sti` are little-endian 32-bit accesses and an unaligned address is rounded down; `pld` and `pst` wrap the offset at 12 bits and reach the registers r0..r7. Evidence: [`memory`](14-evidence.md#1424-memory-run-1), [`indirect`, device run 1](14-evidence.md#1425-indirect-run-1), [`indirect`, device run 2](14-evidence.md#14211-indirect-run-2), [`indirect`, device run 3](14-evidence.md#14217-indirect-run-3).
- **Inferred.** Opcodes `18` and `19` load and store the register window at a register-held offset; the original programs use them only on `0xd60..0xd7c` (finding 3). Evidence: [RE-6](14-evidence.md#1436-re-6-opcodes-18-and-19); the device confirms the reach to the whole window ([`indirect`, device run 1](14-evidence.md#1425-indirect-run-1), [`indirect`, device run 2](14-evidence.md#14211-indirect-run-2), [`indirect`, device run 3](14-evidence.md#14217-indirect-run-3), [`fmcmap`](14-evidence.md#14246-fmcmap-run-11)).
- **Device.** Window offsets are 12 bits wide: `wr`, `st` and `ld` ignore bits 15:12 of `arg`. Branch targets and writes to r8 use bits 24:12 of the target and ignore bit 31. `jr` does not jump when the register value has bit 12, 16, 24 or 31 set. Evidence: [`fwidth`](14-evidence.md#142100-fwidth-run-27).
- **Device.** Register numbers of 8 and above behave as follows. As a source in the argument field, numbers 9, 15 and 255 read r0. As a source in the register field and as the address register of `ldi`, numbers 9 and 14 read 0. As a destination, numbers 9, 11..16, 24 and 255 change nothing. Number 8 is the PC, and a write to number 10 goes to r0..r7. Numbers 24 and 26 do nothing, so the whole register field is decoded. Evidence: [`regnum`](14-evidence.md#14259-regnum-run-15), [`r8`, device run 16](14-evidence.md#14273-r8-run-16), [`r8`, device run 17](14-evidence.md#14279-r8-run-17). **Open:** the behaviour of register 8 as a `st` source, as an `ldi` address register and in `bnz` was not tested or is inferred (finding 69).
- **Device.** `bz` and `bnz` ignore `arg`, test all 32 bits of the register and take unaligned targets as given. `wait` ignores `arg` and `imm`, and a `wait` on an event number above 15 never passes. Evidence: [`branch`](14-evidence.md#14260-branch-run-15), [`waitf`](14-evidence.md#14261-waitf-run-15).
- **Device.** The fields the original programs leave 0 (`imm` of `st`, `ldi`, `mov`, `sti`, `pld`, `pst`, `R` of `wr`, `arg` of `movi`) are ignored; `end` faults when `R` or `arg` is non-zero and ignores `imm`. Evidence: [`fields0`](14-evidence.md#142106-fields0-run-28).
- **Device.** The program can write the PC (`0xc38`, which is r8); such a write is a jump. An `ld` of `0xc38` reads the offset of that instruction. The CPU can write the PC only while the program is stopped at a pause (opcode `12`). Evidence: [`pcwrite`](14-evidence.md#14296-pcwrite-run-27), [`r8`, device run 16](14-evidence.md#14273-r8-run-16), [`r8`, device run 17](14-evidence.md#14279-r8-run-17), [`op12cont`](14-evidence.md#14297-op12cont-run-27).
- **Device.** Register numbers 8..255 in every role ([chapter 4, section 4.3](04-sequencer-memory-map.md#43-register-file-r0r7-the-pc-and-register-numbers-above-7)). **Device.** `st` with a register number from 8 to 255 stores the last value that passed through the register file: the value the previous instruction wrote into a register, or the register value it read (r5 after `st [..], r5`, r0 after `nop` and `wr`, whose register field is 0); `wait` leaves it unchanged. **Inferred:** a number above 7 in the register field selects no register, and the register file's output keeps the last value it carried. `bnz` and `bz` with these numbers never branched, so they do not test that value. Evidence: [`regnum`](14-evidence.md#14259-regnum-run-15), [`regsweep`](14-evidence.md#142149-regsweep-run-35), [`stprev`](14-evidence.md#142156-stprev-run-36).

## 15.2 Opcodes

- **Device.** Of all 256 opcode values only the 19 used by the original programs and `08`, `09`, `0f`, `10`, `12`, `15`, `16`, `ff` do not fault. The opcode byte is decoded in all 8 bits: the values `20`, `40` and `80`, each being `00` with one high bit set, fault like the other illegal values instead of acting as `end`. The other values stall for about 4.87 ms and then fault, with no other effect. Evidence: [`opsweep`](14-evidence.md#14243-opsweep-run-11), [`unknown`, device run 1](14-evidence.md#1428-unknown-run-1), [`unknown`, device run 2](14-evidence.md#14214-unknown-run-2), [`unknown`, device run 3](14-evidence.md#14220-unknown-run-3).
- **Device.** `08` and `ff` have no visible effect in any operand form, cost the time of `movi` and do not react to pending flags. Evidence: [`optime`](14-evidence.md#14244-optime-run-11), [`opstate`](14-evidence.md#14290-opstate-run-24). **Open:** why there are two nop instructions (`08` nop, `ff` nop2) that behave the same way.
- **Device.** `0f` jumps to the byte offset held in the register named by `arg`, unrounded, with no return address kept. Evidence: [`op0f`](14-evidence.md#14251-op0f-run-14).
- **Device.** `10` sets `CS_IRQ` bit 1 and continues, whatever flags are pending; it did not raise the CPU interrupt line. Evidence: [`op10`](14-evidence.md#14232-op10-run-6), [`opstate`](14-evidence.md#14290-opstate-run-24), [`irqline`, device run 15](14-evidence.md#14267-irqline-run-15), [`irqline`, device run 16](14-evidence.md#14270-irqline-run-16), [`irqline`, device run 17](14-evidence.md#14276-irqline-run-17).
- **Device.** `12` stops the program, with no timeout, in every operand form and state. While it is stopped, `CS_IRQ` bit 3 is set, `C08` reads `0xa`, `FMSS_CTRL` bit 18 is set and the instruction is held in `0xc40` and `0xc44`. Of eighteen kinds of CPU write tried, only one released it: writing the PC (normally to the offset of the pause instruction + 8) and then a start word, which continues the program. Evidence: [`op12`](14-evidence.md#14224-op12-run-5), [`op12wait`](14-evidence.md#14240-op12wait-run-11), [`op12ack`](14-evidence.md#14231-op12ack-run-6), [`op12rel`](14-evidence.md#14263-op12rel-run-15), [`op12cont`](14-evidence.md#14297-op12cont-run-27), [`opstate`](14-evidence.md#14290-opstate-run-24). A start word without a PC write continues at the pause itself ([`op12ack`](14-evidence.md#14231-op12ack-run-6), [`op12cont`](14-evidence.md#14297-op12cont-run-27)). **Reading (inferred):** `12` is a pause (breakpoint) instruction for debugging programs: it stops the program where it is, raises `CS_IRQ` bit 3, ignores its fields, and the CPU continues it by writing the PC (`0xc38`) and a start word. The behaviour is a device result; "for debugging" is the reading of that behaviour.
- **Device.** `15` waits until the timer `C14`, counting down from a non-zero value, reaches 0 (about 4.85 ms); if `C14` is already 0, the instruction loads `0xff` into it at once. Evidence: [`op15`](14-evidence.md#14223-op15-run-4), [`c14`](14-evidence.md#14227-c14-run-5).
- **Device.** `16` waits for any event flag of either register set or of the ECC engine and then continues at the fault vector `C4C`, with no fault raised; with nothing pending it times out and faults. It waits for a flag that arrives during the wait; `C58` makes no difference. Evidence: [`op16`](14-evidence.md#14289-op16-run-23), [`op16b`](14-evidence.md#14291-op16b-run-24), [`opstate`](14-evidence.md#14290-opstate-run-24).
- **Device.** `09` (`wait2`) continues at once while the interrupt line it names is raised and otherwise times out like an unmet `wait`; `arg` and `imm` are ignored. Evidence: [`op09`](14-evidence.md#14292-op09-run-24), [`op09b`](14-evidence.md#14293-op09b-run-25), [`op09c`](14-evidence.md#14294-op09c-run-26), [`op09d`](14-evidence.md#14299-op09d-run-27), [`w2vic`](14-evidence.md#142171-w2vic-run-38).

## 15.3 Events, waits and the timeout

- **Inferred.** `wait` events 0..5 pair with these flags: `wait` event 0 with `FMC_STATUS` bit 1, event 1 with bit 2, event 2 with bit 20, event 3 with bit 3, event 4 with `ECC_DONE` bit 0, and event 5 with `FMC_STATUS` bit 23 (finding 4); the pairing is taken from the flag that each wait in the original programs acknowledges. Evidence: [RE-7](14-evidence.md#1437-re-7-wait-event-5-shape), [RE-12](14-evidence.md#14312-re-12-ecc-protocol-in-read); the page-read experiment confirms the pairing of `wait` events 1, 0, 3, 4 and 2 with the address, command, transfer, ECC and DMA steps respectively ([`readev`, device run 15](14-evidence.md#14258-readev-run-15), [`readev`, device run 16](14-evidence.md#14269-readev-run-16), [`readev`, device run 17](14-evidence.md#14275-readev-run-17), [`readev`, device run 21](14-evidence.md#14286-readev-run-21)).
- **Device.** With nothing pending, a `wait` on events 0..10 and 12..15 times out after 4 865..4 882 us, while `wait` event 11 passes at once. Event 11 also passes during a block erase and with any chip enable selected, so it is not the chips' ready line. Evidence: [`wait`, device run 1](14-evidence.md#1427-wait-run-1), [`wait`, device run 4](14-evidence.md#14222-wait-run-4), [`ev11`](14-evidence.md#14241-ev11-run-11), [`evsweep`, device run 11](14-evidence.md#14247-evsweep-run-11), [`evsweep`, device run 14](14-evidence.md#14250-evsweep-run-14).
- **Device.** Events are levels and are not consumed; a sequencer read of `FMC_STATUS` or `FMC_NSTAT` does not consume an event. Evidence: [`evcons`](14-evidence.md#14282-evcons-run-18), [`evclear`](14-evidence.md#14253-evclear-run-14).
- **Device.** `wait` event 4 passes when any `ECC_DONE` bit except bit 4 is set. `wait` events 6, 7, 8 and 9 are the command, address, DMA and transfer flags of the second register set. `wait` event 15 passes while an enabled NAND controller (FMC) or ECC interrupt source is pending (inferred from its passing only when `0x044` was non-zero). Evidence: [`evcons`](14-evidence.md#14282-evcons-run-18), [`ev8`](14-evidence.md#14281-ev8-run-18), [`dmaloop`, device run 20](14-evidence.md#14284-dmaloop-run-20), [`dmaloop`, device run 21](14-evidence.md#14287-dmaloop-run-21), [`evsweep`, device run 11](14-evidence.md#14247-evsweep-run-11), [`evsweep`, device run 14](14-evidence.md#14250-evsweep-run-14), [`op09d`](14-evidence.md#14299-op09d-run-27). **Device.** In a clean state with the interrupt enables clear, `wait` event 15 never passed ([`state`, device run 17](14-evidence.md#14274-state-run-17), [`state`, device run 18](14-evidence.md#14280-state-run-18)).
- **Device.** A `wait` times out after about 4.87 ms with start word `0xfff5`, whatever `C58` holds; `C58` bit 2 decides whether the program then continues at the fault vector or at the next instruction; and start-word bit 2 enables the timeout. Evidence: [`wait`, device run 1](14-evidence.md#1427-wait-run-1), [`wait`, device run 4](14-evidence.md#14222-wait-run-4), [`c58`, device run 2](14-evidence.md#14213-c58-run-2), [`c58`, device run 3](14-evidence.md#14219-c58-run-3), [`c58ill`](14-evidence.md#14225-c58ill-run-5), [`ctrlfx`](14-evidence.md#14298-ctrlfx-run-27), [`ctrlbits`](14-evidence.md#14245-ctrlbits-run-11).
- **Device.** The timeout length is (start-word bits 15:8 + 1) x 2^s bus cycles. Here s = 3, 5, 7, 9 and 10 for start-word bits 7:4 = 1..5, and s = 11 for bits 7:4 of 6 and above; bits 7:4 = 0 give an immediate timeout. The bus clock of about 108 MHz is inferred. Evidence: [`tmofield`](14-evidence.md#142107-tmofield-run-28), [`tmobits`](14-evidence.md#142110-tmobits-run-29), [`tmobits2`](14-evidence.md#142120-tmobits2-run-30).
- **Device.** `C58` bit 0 at an END sets `C5C` and makes every later END run the fault vector once; `C58` bit 1 diverts one END when the CPU first wrote `C58 = 2` and afterwards wrote `C4C`; `C10`, `C3C`, `C48` and `C54` do not change the timeout. Evidence: [`resume`](14-evidence.md#14221-resume-run-4), [`pending`, device run 5](14-evidence.md#14226-pending-run-5), [`pending`, device run 6](14-evidence.md#14230-pending-run-6), [`oneshot`](14-evidence.md#14236-oneshot-run-8), [`timeregs`](14-evidence.md#14254-timeregs-run-14). **Open:** the mechanism of `C58` bit 1 (inferred: armed by the CPU write of `C4C`).
- **Device.** `C14` is the timeout timer. A `wait` that starts waiting loads it with `0xff`, and it then counts down. It reads `0xff` after a timeout, is frozen at the end of the program, and ignores writes. Evidence: [`c14`](14-evidence.md#14227-c14-run-5), [`op15`](14-evidence.md#14223-op15-run-4), [`c08`](14-evidence.md#14256-c08-run-15).
- **Device.** `wait` event 5 passes about 155 us into a block erase when a status poll is taken during it (the status byte changes from `0x81` to `0xc0`), and passes at once on an idle chip. Evidence: [`ev5`](14-evidence.md#14242-ev5-run-11).
- **Device.** `wait` event 5 is `FMC_STATUS` bit 23 as a level; a status latch sets it only while `wait` event 5 is armed, and uses the arm (the arming rule is in the next statement); after a latch a new command is refused until `FMCTRL1 = 0x20`; a latch after `90h` sets no bit 23. Evidence: [`ev5rule`](14-evidence.md#14255-ev5rule-run-15).
- **Device.** A status latch sets bit 23 only while `wait` event 5 is armed and uses the arm; `FMCTRL1` operations (the set-up word, `0x100e0`, a transfer from the chip, a DMA) and address cycles re-arm it, and so does the polled chip becoming ready; `FMCTRL1 = 0x20`, the status-clear word, a CE deselect and reselect, and an ECC operation do not. Evidence: [`ev5ready`](14-evidence.md#142121-ev5ready-run-30), [`ev5arm`](14-evidence.md#142124-ev5arm-run-31), [`ev5two`](14-evidence.md#142127-ev5two-run-32).
- **Device.** With `FMC_DATA_SEL = 0x100` a status latch returns the last command byte (`0x70`), not the status. Evidence: [`writeseq`](14-evidence.md#142115-writeseq-run-29), [`pageorder`](14-evidence.md#142122-pageorder-run-30).
- **Open.** A `wait` event 5 straight after "`70h`, latch" timed out although `FMC_STATUS` bit 23 read set afterwards. The same latch passed after `70h`, `wait` event 0 and clearing `FMC_STATUS` bit 1. One status-latch `wait` event 5 timed out in one of two identical runs. One `wait` event 3 with CE0 selected passed in one program and timed out in three programs run after it. Evidence: [`evsweep`, device run 11](14-evidence.md#14247-evsweep-run-11), [`evsweep`, device run 14](14-evidence.md#14250-evsweep-run-14), [`evclear`](14-evidence.md#14253-evclear-run-14), [`ev5t`, device run 16](14-evidence.md#14272-ev5t-run-16), [`ev5t`, device run 17](14-evidence.md#14278-ev5t-run-17), [`op16`](14-evidence.md#14289-op16-run-23).
- **Open.** `FMC_STATUS` bit 24 appeared instead of bit 23 in both status-latch programs of `irqsrc` that wrote an interrupt enable and in one program of `op16` with none, and in none of the fifteen programs of `ev5en`; the enables are not shown to cause it. Evidence: [`irqsrc`](14-evidence.md#142101-irqsrc-run-27), [`op16`](14-evidence.md#14289-op16-run-23), [`ev5en`](14-evidence.md#142109-ev5en-run-28). Findings 104, 110.
- **Device.** `C14` reloads with start-word bits 15:8, so the timeout length field is the counter's start value. Evidence: [`startbits`](14-evidence.md#142132-startbits-run-35).
- **Device.** `wait2` condition 33 passed while the chip was idle in [`op09w33`](14-evidence.md#142123-op09w33-run-30) and during an ECC operation and a DMA in [`finale`](14-evidence.md#142130-finale-run-34); it did not pass in [`op09nand`](14-evidence.md#142116-op09nand-run-29) (idle and during an erase), [`evsweep2`](14-evidence.md#142137-evsweep2-run-35), [`ctrlwords`](14-evidence.md#142139-ctrlwords-run-35), [`w2state`](14-evidence.md#142151-w2state-run-36), [`blk100b`](14-evidence.md#142168-blk100b-run-37) or [`w2vic`](14-evidence.md#142171-w2vic-run-38).
- **Device.** `wait2` condition N is interrupt source N of the CPU's interrupt controllers, read from their raw status: VIC0 line N for N = 0..31, VIC1 line N - 32 for N = 32..63; 64 of 64 conditions matched the raw lines in four states. Condition 20 is the NAND controller's line, condition 43 the ECC engine's line; conditions 5 and 33 are lines of other devices. **Inferred:** `wait2` lets a program wait for any interrupt source of the SoC, not only for the FMSS engine's own flags. Evidence: [`w2vic`](14-evidence.md#142171-w2vic-run-38), [`w2state`](14-evidence.md#142151-w2state-run-36).

## 15.4 Control registers

- **Device.** `CS_IRQ` bit 0 is END, bit 1 is set by opcode `10`, bit 2 is a fault, and bit 3 is set while opcode `12` blocks. Bits 6:4 follow the NAND controller and ECC interrupt sources once these are enabled in `0x044` and `0x844`. Bit 6 reflects the pending `ECC_DONE` bits. Evidence: [`op10`](14-evidence.md#14232-op10-run-6), [`op12`](14-evidence.md#14224-op12-run-5), [`irqen`, device run 16](14-evidence.md#14271-irqen-run-16), [`irqen`, device run 17](14-evidence.md#14277-irqen-run-17), [`irqsrc`](14-evidence.md#142101-irqsrc-run-27).
- **Device.** `C08` is a state code: 1 means running, 4 waiting or stalled on an illegal opcode, 3 paused by start-word bit 1, `0xa` blocked on `12`, and 0 idle or held; 5 is the value seen when the program itself reads `C08`. Evidence: [`c08`](14-evidence.md#14256-c08-run-15), [`ctrlhold`](14-evidence.md#14252-ctrlhold-run-14). **Open:** the full code set.
- **Device.** `C50` bits 5:0 each follow the pending flag of events 0..5; bit 0 stayed clear inside the handlers of a timeout and of an illegal opcode, with and without an acknowledge of the pending flag. Evidence: [`c50`](14-evidence.md#14237-c50-run-9), [`c50x`](14-evidence.md#14249-c50x-run-13), [`op16`](14-evidence.md#14289-op16-run-23), [`irqsrc`](14-evidence.md#142101-irqsrc-run-27). **Inferred:** the original handlers' test of bit 0 reads as "a command flag is still pending". **Device.** No fault tried set `C50` bit 0 ([`holdout`, device run 9](14-evidence.md#14238-holdout-run-9), [`holdout`, device run 10](14-evidence.md#14239-holdout-run-10)). **Open:** which fault, if any, sets it, and bit 8 after a soft reset.
- **Device.** Start-word bit 0 starts the sequencer. Bit 1 pauses it before the first instruction, or exactly where the program is during a run, until a start word without bit 1 is written. Bits 3 and 16 hold the sequencer in the post-reset state or abort a running program, which restarts from instruction 0 on release. Bit 2 enables the timeout, and bits 15:4 set the timeout. Bit 17 does not clear registers. There is no single-step. Evidence: [`ctrlbits`](14-evidence.md#14245-ctrlbits-run-11), [`ctrlhold`](14-evidence.md#14252-ctrlhold-run-14), [`pause`](14-evidence.md#14264-pause-run-15), [`ctrlfx`](14-evidence.md#14298-ctrlfx-run-27), [`tmofield`](14-evidence.md#142107-tmofield-run-28).
- **Open.** Start-word bit 6 (compared between the start words `0xfff5` and `0xffb5`): no effect on the timeout length, the CPU interrupt line, loops, waits, illegal opcodes, `evjmp`, program fetch, `ldi` / `sti` / `pld`, DMA, ECC or reserved-word access was found, and the reading "bit 6 = interrupt enable" is not confirmed. Accesses to different parts of the NAND under the two start words were not compared. Evidence: [`irqline`, device run 15](14-evidence.md#14267-irqline-run-15), [`ctrlfx`](14-evidence.md#14298-ctrlfx-run-27), [`ctrlbits`](14-evidence.md#14245-ctrlbits-run-11), [`startbits`](14-evidence.md#142132-startbits-run-35), [`startdiff`](14-evidence.md#142131-startdiff-run-35). Findings 54, 153.
- **Device.** After `FMSS_CTRL = 0x30000` the first start fetches instruction 0 into `0xc40`/`0xc44` and executes it only if it is `end`; any other instruction is left waiting, with `FMSS_CTRL` bit 18 set, until a second start. Evidence: [`startseq`](14-evidence.md#14229-startseq-run-6), [`startseq2`](14-evidence.md#14234-startseq2-run-7), [`startseq3`](14-evidence.md#14235-startseq3-run-8).
- **Device.** The CPU write masks, in writable bits, are 32 for `0xc04`, r0..r7, `0xc3c`, `0xc48` and `0xc4c`; 8 for `0xc10`; 12 for `0xc54`; 8 for `0xc58`; and 1 for `0xc5c`. The words `0xc08`, `0xc14`, `0xc38`, `0xc40`, `0xc44` and `0xc50` are read-only. `C48` and `C54` are cleared at a start and kept after the end; `C3C` reads 0 after a run and held the vector address in a handler (inferred: the address of the last vector taken). Evidence: [`rwmask`](14-evidence.md#14248-rwmask-run-12), [`access`](14-evidence.md#142105-access-run-27), [`timeregs`](14-evidence.md#14254-timeregs-run-14).
- **Device.** `C3C` inside a handler is the offset of the faulting instruction + 8. **Inferred:** it is the return address of the fault, the instruction after the one that faulted. Evidence: [`ctrlwords`](14-evidence.md#142139-ctrlwords-run-35), [`c50fault`](14-evidence.md#142138-c50fault-run-35).

## 15.6 NAND controller

- **Device.** `FMC_CTRL0` bit 24 enables DMA: with it clear no DMA runs in either direction and either register set; with it set, a loopback from RAM into the data buffer and back to RAM returns 512 bytes intact. A DMA always moves 512 bytes whatever `FMC_DNUM` says. Evidence: [`dmaloop`, device run 20](14-evidence.md#14284-dmaloop-run-20), [`dmaloop`, device run 21](14-evidence.md#14287-dmaloop-run-21), [`readev`, device run 15](14-evidence.md#14258-readev-run-15), [`readev`, device run 16](14-evidence.md#14269-readev-run-16), [`readev`, device run 17](14-evidence.md#14275-readev-run-17), [`readev`, device run 21](14-evidence.md#14286-readev-run-21), [`bufsize`](14-evidence.md#142103-bufsize-run-27).
- **Device.** For one sector of a page read, the NAND transfer of 512 bytes takes 49 us, the ECC decode event passes at once, the DMA to RAM takes 14 us (about 36 MB/s), and the whole time from the command to the data in RAM is 123 us. Evidence: [`readev`, device run 15](14-evidence.md#14258-readev-run-15), [`readev`, device run 16](14-evidence.md#14269-readev-run-16), [`readev`, device run 17](14-evidence.md#14275-readev-run-17), [`readev`, device run 21](14-evidence.md#14286-readev-run-21).
- **Device.** The second register set runs a READ ID (command, address, 8-byte transfer counted in `0x424`), has its own data buffer and DMA engine, and its DMA flag is `wait` event 8. No chip answered on it, with or without its pins switched; chip enables CE0..CE3 on the first set answered. Evidence: [`ev8`](14-evidence.md#14281-ev8-run-18), [`dmaloop`, device run 20](14-evidence.md#14284-dmaloop-run-20), [`dmaloop`, device run 21](14-evidence.md#14287-dmaloop-run-21), [`chan1`](14-evidence.md#14257-chan1-run-15), [`chan1pins`](14-evidence.md#14295-chan1pins-run-27). **Inferred:** only channel 0 is used on this board, from the boot ROM's two-channel pin set-up ([RE-43](14-evidence.md#14343-re-43-boot-rom-nand-access)) and the single board tested. Findings 73, 79, 82, 93, 100.
- **Device.** `FMC_STATUS` bit 27 is set after every written sector read and clear after every erased one: it means that the sector that was read had been written. Evidence: [`rawpage`](14-evidence.md#142113-rawpage-run-29), [`rawwrite`](14-evidence.md#142114-rawwrite-run-29). Bit 27 is set for sectors with and without stored errors; the third-party driver classifies it as "programmed page" (3p).
- **Device.** `wait2` does not wait on the second register set's flags: with each second-set flag pending alone, `wait2` conditions 0 to 15 were tried and only condition 5 passed (condition 33 was outside that range); `wait` events 6, 7, 8 and 9 passed in the same states. Evidence: [`op09d`](14-evidence.md#14299-op09d-run-27).
- **Device.** `FMC_DMA_CTRL` = 7 is needed for the drain with `FMCTRL1` = `0x1e0` to deliver correct data; `FMC_CTRL0` bits 9, 11 and 24 made no difference to a page read. Evidence: [`fmcbits`](14-evidence.md#142143-fmcbits-run-35).
- **Device.** As seen from the CPU, `FMC_28` changes only between runs; a DMA and the set-up word reset it. **Inferred:** CPU reads of some window word advance it (the dumps read every word). Evidence: [`fmc28b`](14-evidence.md#142135-fmc28b-run-35).
- **Device.** The FIFO port `FMC_FIFO` advances `FMC_28` by 4 per read and returned 0 from data buffers filled by DMA. **Inferred:** `FMC_28` is the FIFO port's byte position; the READ ID bytes are held in storage the DMA does not fill, or are read from a data buffer only after a chip transfer (open). Evidence: [`bufport`](14-evidence.md#142154-bufport-run-36).
- **Device.** `FMC_DMA_CTRL` bits 1, 2 and 4..7 each make DMAs fail, and the value persists between runs. **Inferred:** the wrong data of the `0x102` / `0x1e0` drains in [`fmcbits`](14-evidence.md#142143-fmcbits-run-35) came from `FMC_DMA_CTRL` = `0xff` left by the case before them. Evidence: [`dmactl`](14-evidence.md#142164-dmactl-run-37), [`fmcbits`](14-evidence.md#142143-fmcbits-run-35).
- **Device.** Patterns DMA-ed through the second register set into its parity buffer 0 appeared in the first set's parity buffer 0. **Inferred:** the two register sets share parity buffer 0 (and perhaps all buffers). Evidence: [`ch1buf`](14-evidence.md#142166-ch1buf-run-37).

## 15.7 ECC codes and modes

- **Device.** The engine corrects up to 8 data bits per sector with `ECC_MODE = 0x180`; 9..12 flipped bits give `ECC_RESULT = 0x11` and leave the data as it was sent; `ECC_DONE` is `0x35` for a decode and `0x3d` after an uncorrectable one. A decode in a separate program from its encode reports every sector uncorrectable (inferred: the set-up word clears the buffers). Evidence: [`eccstr`](14-evidence.md#142104-eccstr-run-27), [`eccstr2`](14-evidence.md#142108-eccstr2-run-28), [`eccpar`](14-evidence.md#142102-eccpar-run-27).
- **Device.** After an encode the 13 parity bytes are in `0x900..0x90c` and the parity slot can be copied out by DMA. Zero data gives non-zero parity because the three metadata bytes (`0xff` there) are part of the code word. Evidence: [`eccpar`](14-evidence.md#142102-eccpar-run-27), [`eccstr2`](14-evidence.md#142108-eccstr2-run-28). The metadata bytes enter the parity.
- **Device.** Every measured parity matches binary BCH, t = 8, over GF(2^13) (`0x201b`), generator of degree 104, message = 512 data bytes + 3 slot metadata bytes, checked against a computed code word for all twelve encodes. Evidence: [`eccstr2`](14-evidence.md#142108-eccstr2-run-28), [`eccpar`](14-evidence.md#142102-eccpar-run-27).
- **Device.** Pages written by the original firmware are code words of this code with their real metadata in slot bytes 0..2 (20 sectors); raw writes of chunks built by the CPU read back as written; errors stored on the flash decode as the identified code predicts (8 corrected, 9 not; errors in metadata and parity bits are corrected and counted). Evidence: [`rawpage`](14-evidence.md#142113-rawpage-run-29), [`rawwrite`](14-evidence.md#142114-rawwrite-run-29), [`eccchunk`](14-evidence.md#142112-eccchunk-run-29), [`eccchunk2`](14-evidence.md#142118-eccchunk2-run-30).
- **Device.** A parity buffer is 64 bytes; a 512-byte DMA into it wraps and leaves the source's last 64 bytes; the metadata path fills slot bytes 0..2 in order. Evidence: [`eccchunk`](14-evidence.md#142112-eccchunk-run-29).
- **Device.** `ECC_MODE` bits: bit 8 selects the slot path. Bit 15 selects a Reed-Solomon code over GF(2^10) with byte symbols. Bits 3:2 together with bit 15 select 8, 12 or 16 parity symbols, which correct 4, 6 and 8 bad bytes (measured; beyond that the sector is uncorrectable). A Reed-Solomon encode and decode ignore the slot field and use slot 0; the 16-symbol parity (20 bytes) fills slot 0 and the first 4 bytes of slot 1. Bit 4 swaps the bytes of each 32-bit word. Bits 20:16 are the data length L. `ECC_DONE` bit 3 is the sticky uncorrectable flag. Evidence: [`finale`](14-evidence.md#142130-finale-run-34), [`b15ecc`](14-evidence.md#142128-b15ecc-run-32), [`rsdecode`](14-evidence.md#142133-rsdecode-run-35), [`rschip`](14-evidence.md#142161-rschip-run-37). **Inferred:** of the three Reed-Solomon strengths, the 16-symbol form does not fit a 4 KiB page with 128 spare bytes in the 16-byte chunk layout (8 x 532 > 4224), and none of them protects the metadata bytes ([chapter 10, section 10.9](10-ecc-engine.md#109-what-is-stored-on-the-chip)).
- **Device.** Without bit 8 (`ECC_MODE` 0, `0x80`, `0xe00000`) no code is computed: the n-th such operation since start-up writes the n-th value of a fixed sequence of 61 distinct values into `0x900..0x90c` and `0x990`, whatever the data or the mode; a decode does not advance it and every decode is uncorrectable. Evidence: [`eccmode2`](14-evidence.md#142119-eccmode2-run-30), [`eccmode4`](14-evidence.md#142129-eccmode4-run-33), [`finale`](14-evidence.md#142130-finale-run-34). **Open:** what generates the sequence and which event restarts it (between two device runs ([chapter 13, section 13.2](13-experiments.md#132-device-runs)) it restarted once and continued once). Findings 118, 137, 144. In `seqrestart` no action tried restarts the sequence ([`seqrestart`](14-evidence.md#142146-seqrestart-run-35)); the first such operation can give value 1 (`eccregs`, `eccmode4`) or continue the sequence (`finale`: value 14) (**inferred:** a power cycle restarts it, not tested).
- **Inferred.** Byte order ([chapter 10, section 10.14](10-ecc-engine.md#1014-byte-order)): the FMSS engine is little-endian in instruction fields, words and the ECC area, while the parity in the slot and on the flash is stored most significant byte first. The reading is that the parity order is the bit-serial convention of the code (the division runs over a most-significant-bit-first stream, so the highest-order parity byte comes first), and that `ECC_MODE` bit 4 is an optional byte swap of each 32-bit word for data held in the other order. Evidence: [`eccpar`](14-evidence.md#142102-eccpar-run-27), [`eccmode2`](14-evidence.md#142119-eccmode2-run-30), [`finale`](14-evidence.md#142130-finale-run-34). The parity byte orders and the effect of bit 4 are device results; the explanation is not tested.
- **Device.** No mode corrects more than 8 scattered bits per 512-byte sector. Evidence: [`eccstr2`](14-evidence.md#142108-eccstr2-run-28), [`b15ecc`](14-evidence.md#142128-b15ecc-run-32), [`finale`](14-evidence.md#142130-finale-run-34).
- **Device.** A Reed-Solomon operation ignores the slot field and uses slot 0. **Inferred:** a Reed-Solomon page needs each sector's chunk moved to and from slot 0 around its encode and decode, so the engine's four-slot layout serves only the BCH code. Evidence: [`rschip`](14-evidence.md#142161-rschip-run-37).

Evidence: [`writeseq`](14-evidence.md#142115-writeseq-run-29), [`writeseq2`](14-evidence.md#142125-writeseq2-run-31), [`pageorder`](14-evidence.md#142122-pageorder-run-30), [`eraseseq`](14-evidence.md#142117-eraseseq-run-29).

Evidence: [RE-5](14-evidence.md#1435-re-5-prologue-values), [RE-7](14-evidence.md#1437-re-7-wait-event-5-shape), [RE-9](14-evidence.md#1439-re-9-control-word-and-chip-enable-changes), [RE-12](14-evidence.md#14312-re-12-ecc-protocol-in-read), [RE-13](14-evidence.md#14313-re-13-page-verdict-in-read), [RE-15](14-evidence.md#14315-re-15-page-stream), [RE-16](14-evidence.md#14316-re-16-meta-engine-use), [RE-17](14-evidence.md#14317-re-17-read-batches), [RE-18](14-evidence.md#14318-re-18-page-word-and-fmc_status-b27), [RE-19](14-evidence.md#14319-re-19-dma-address-and-dma-control), [RE-21](14-evidence.md#14321-re-21-two-plane-status-polls), [RE-22](14-evidence.md#14322-re-22-program-fail-path), [RE-23](14-evidence.md#14323-re-23-erase-sequence), [RE-24](14-evidence.md#14324-re-24-readid-sequence), [RE-25](14-evidence.md#14325-re-25-fault-handlers).

## 15.10 Original firmware (reverse engineering)

- **Observed.** The nine programs, their locations, sizes and command orders are in [RE-1](14-evidence.md#1431-re-1-nine-sequencer-programs-in-the-ipod-os-image), [RE-2](14-evidence.md#1432-re-2-program-table), [RE-3](14-evidence.md#1433-re-3-program-locations-as-memory-addresses); all use the same prologue ([RE-5](14-evidence.md#1435-re-5-prologue-values)) and the opcode set of [RE-4](14-evidence.md#1434-re-4-instruction-encoding-and-opcode-set-used-by-the-programs).
- **Observed.** The original CPU driver starts a program with `CS_IRQ = 0xff` and `FMSS_CTRL = 0xfff5`, polls VIC1 raw bit 22 for up to 2000 ms, classifies by `CS_IRQ` bits 2 and 0, resets the sequencer by writing `FMSS_CTRL` = `0x30000` after a failure, and never reads `CS_STATUS` or the PC ([RE-31](14-evidence.md#14331-re-31-cpu-driver-start), [RE-32](14-evidence.md#14332-re-32-cpu-driver-wait-and-classify), [RE-33](14-evidence.md#14333-re-33-cpu-driver-reset), [RE-34](14-evidence.md#14334-re-34-cpu-driver-clear), [RE-40](14-evidence.md#14340-re-40-cpu-driver-other-sequencer-registers)).

- **Inferred.** The 16-byte chunk is 13 bytes of parity plus a 3-byte metadata fragment (finding 14): the BCH parity length of 13 bytes and the 4-bit count field are consistent with it, and the chunk bytes read from pages written by the original firmware contain the real metadata in slot bytes 0..2 ([RE-15](14-evidence.md#14315-re-15-page-stream), [RE-16](14-evidence.md#14316-re-16-meta-engine-use), [`rawpage`](14-evidence.md#142113-rawpage-run-29)).
- **Observed.** `wait` event 5 is used 19 times. 13 uses (all outside ERASE) have one five-instruction shape with the ready test in microcode, and the 6 uses in ERASE stage their waits with `C58` = 0 ([RE-7](14-evidence.md#1437-re-7-wait-event-5-shape), [RE-8](14-evidence.md#1438-re-8-erase-ready-waits)). **Device:** a timeout with `C58` bit 2 clear continues at the next instruction ([`c58`, device run 2](14-evidence.md#14213-c58-run-2), [`c58`, device run 3](14-evidence.md#14219-c58-run-3)).
- **Inferred.** A program is the span from its prologue to its last opcode-00 instruction; the instructions from the fault vector offset (`C4C`) to that last instruction are the program's fault tail (run when a fault takes the vector), and the opcode-00 instruction just before that offset ends the normal path. Evidence: [RE-1](14-evidence.md#1431-re-1-nine-sequencer-programs-in-the-ipod-os-image), [RE-5](14-evidence.md#1435-re-5-prologue-values).
- **Inferred.** Opcode `19` stores the one-hot chip mask of the chip just accepted into a READ batch, at an address that starts at `0xd60` and advances by 4; opcode `18` loads it back, once per transfer; The parameter word `0xd50` holds the parameter-RAM offset that the second `pld` (at READ+0x6e0) reads next: it starts at `0xd64` and READ adds 4 after each load. The offsets used are `0xd60..0xd7c`. Evidence: [RE-6](14-evidence.md#1436-re-6-opcodes-18-and-19), [RE-17](14-evidence.md#14317-re-17-read-batches).
- **Inferred.** The five-instruction group of `wait` event 5 is a ready test in the sequencer program: `FMCTRL1 = 0xca` starts the NAND status poll, `FMC_NSTAT` bit 6 is the ready flag, a set flag skips the `wait` event 5, and the flag is not tested again after the wait. ERASE does the same test in its six uses, but stages `C58` around them (`C58 = 0` before the first wait, `C58 = 4` before the third) and writes `C14 = 0xff` and `CS_IRQ = 4` after the first two; why it does so is open. Evidence: [RE-7](14-evidence.md#1437-re-7-wait-event-5-shape), [RE-8](14-evidence.md#1438-re-8-erase-ready-waits), [RE-23](14-evidence.md#14323-re-23-erase-sequence).
- **Inferred.** `FMC_CTRL0` bits 8:1 select the chip enables (the value written is `1 << (CE + 1)`) and every chip change is a read-modify-write that keeps the other bits (mask `0xfffffe01`); bit 24 is set around the DMA phases of READ, RAWREAD and the WRITE programs; the base word `0x801` ORed with the timing word is the setting for the data-transfer programs, while READID uses `0x33201` (bit 9 set instead of bit 11; the reason is open). Evidence: [RE-9](14-evidence.md#1439-re-9-control-word-and-chip-enable-changes), [RE-10](14-evidence.md#14310-re-10-readid-control-word), [RE-35](14-evidence.md#14335-re-35-cpu-driver-timing-word).
- **Inferred.** Writes to `0x80c` with bit 0 set start decodes, and with bit 1 set start encodes ([chapter 10](10-ecc-engine.md)). For each sector READ clears `ECC_DONE` (`0x1ff`), writes the mode `0x180`, starts the decode, waits for `wait` event 4, acknowledges `ECC_DONE` and reads `ECC_RESULT`; the data buffer is moved to memory by DMA after the decode, so the decode works on the buffer before it leaves the controller. Evidence: [RE-12](14-evidence.md#14312-re-12-ecc-protocol-in-read), [RE-14](14-evidence.md#14314-re-14-decode-order).
- **Inferred.** The per-sector verdict in READ is formed as follows. If `ECC_RESULT` bit 0 is set (uncorrectable), bit 30 is put into the page word. Otherwise the corrected-bit count n (bits 19:16, mask `0xf`) sets bit n - 1 of the page word. The page word therefore collects one bit per count seen, the highest set bit marks the largest count, and an all-zero low byte means that no sector reported a non-zero count. Evidence: [RE-13](14-evidence.md#14313-re-13-page-verdict-in-read).
- **Inferred.** READ transfers, per sector, the 16-byte chunk into a slot of the parity buffer (`FMC_24` = 0, 0x10, 0x20, 0x30) and then 512 bytes into a data buffer, sector after sector. WRITE sends the chunk first (from the slot selected by `FMC_28`) and then the data. WRITE runs the meta encode once per page before the first sector's encode and READ runs the meta decode once per page after the last sector's decode; `FMC_METACFG` is always `0x3210`, and the three meta words are `0x060..0x068`. Evidence: [RE-15](14-evidence.md#14315-re-15-page-stream), [RE-16](14-evidence.md#14316-re-16-meta-engine-use).
- **Inferred.** READ issues `30h` for pages on distinct chips before it transfers any of them; a batch ends at the first repeated chip (the new mask overlaps the accumulated mask) or when the page count is exhausted; at most 8 masks are queued because there are 8 chip-enable bits; the per-page results are stored in request order at the address in `0xd24`. Evidence: [RE-17](14-evidence.md#14317-re-17-read-batches), [RE-18](14-evidence.md#14318-re-18-page-word-and-fmc_status-b27).
- **Inferred.** The page word starts as `0x20000000` when `FMC_STATUS` bit 27 stayed clear for the page (an erased page: no ECC data was carried, [chapter 10](10-ecc-engine.md)). The last sector's verdict is added to it, bit 27 is acknowledged at the end of the page, one summary word per page is stored, and all the summary words are ORed into `r6`. Evidence: [RE-18](14-evidence.md#14318-re-18-page-word-and-fmc_status-b27).
- **Inferred.** `FMC_DMA_ADDR` is written once per DMA unit and `FMC_DMA_CTRL = 7` before the last DMA of a run; WRITE reads the DMA list one entry ahead, and the number of entries read is the number of pages times the number of units per page. Evidence: [RE-19](14-evidence.md#14319-re-19-dma-address-and-dma-control), [RE-20](14-evidence.md#14320-re-20-write-dma-list).
- **Inferred.** After `11h` the two-plane programs poll the chip (`70h`, ready test, and a fail test on `FMC_NSTAT` bit 0, written `NSTAT & 1`) before sending `81h`. A failed test jumps at once to the fault tail at the `C4C` offset, where `r6` holds the failing chip-enable mask in bits 7:0 and bit 28 set. Bit 27 is set in READ, READID and RAWREAD unconditionally, and in the other programs only when `C50` bit 0 is set. Evidence: [RE-21](14-evidence.md#14321-re-21-two-plane-status-polls), [RE-22](14-evidence.md#14322-re-22-program-fail-path), [RE-25](14-evidence.md#14325-re-25-fault-handlers).
- **Inferred.** ERASE sends `60h`, three row cycles and `D0h` for each list entry without waiting, then runs a status sweep per chip enable with the staged ready wait; on a normal end `r6` is the mask of the chip enables used. READID sends `FFh` with all eight chip enables selected, runs a software delay (count from `0xd14`), then for each listed chip sends `90h` and one address cycle and reads 8 ID bytes through `FMC_FIFO`, reading the FIFO twice and storing the first word. Evidence: [RE-23](14-evidence.md#14323-re-23-erase-sequence), [RE-24](14-evidence.md#14324-re-24-readid-sequence).
- **Inferred.** RAWREAD reads `4 x P_CHUNKS + 1` blocks of 512 bytes with no parity-chunk handling and no ECC access, and always uses the data buffer selected by `0x102` where READ and WRITE alternate `0x102` and `0x201`. Evidence: [RE-26](14-evidence.md#14326-re-26-rawread).
- **Inferred.** WRITE2P sends `80h .. 11h` then `81h .. 10h`; WRITE2P_78 repeats `80h`; WRITE_78 and WRITE2P_78 poll with `78h` and a three-byte row and test `NSTAT & 3`; WRITECACHE sends `15h` while the remaining page count (`0xd18`) AND the word `0xd44` (0 minus the bank count from `0xd04`) is non-zero, and `10h` otherwise, and ends with a `71h` status sweep. Evidence: [RE-27](14-evidence.md#14327-re-27-write-variants), [RE-46](14-evidence.md#14346-re-46-bank-count-in-writecache).
- **Inferred.** The programs take a list of logical chip numbers (`0xd10`) and a map table (`0xd14`) and turn each entry into a chip-enable bit through the map; READID takes chip-enable indices directly. The 1.1.3 change replaces one `70h` poll (mask 1) per chip enable by four `78h` polls (mask 3) in WRITE_78 and WRITE2P_78. Evidence: [RE-28](14-evidence.md#14328-re-28-releases-101-to-113), [RE-29](14-evidence.md#14329-re-29-chip-addressing-in-the-programs).
- **Inferred.** The original CPU driver's wait function classifies by `CS_IRQ`: `CS_IRQ` bit 2 means a fault (the function prints R0, R2 and R6, resets the sequencer and fails), bit 0 means done, and if neither is set the function reports an unknown interrupt and fails; the timeouts of 2000 ms (wait) and 100 us (clear) hold if the word at `0x3c7000b4` counts microseconds. Resetting is `FMSS_CTRL = 0x30000`, a 1 ms wait, an idle program of one all-zero (opcode `00`) instruction, a start and a 1 ms wait. Evidence: [RE-32](14-evidence.md#14332-re-32-cpu-driver-wait-and-classify), [RE-33](14-evidence.md#14333-re-33-cpu-driver-reset), [RE-34](14-evidence.md#14334-re-34-cpu-driver-clear).
- **Inferred.** The timing word is built from three nanosecond figures per record (c1, c2, c3 = ceil(figure / T)), with T = 1000 divided (integer division) by the value the driver's clock function returns for argument 2, read as the bus clock in MHz; the first triple feeds READ, RAWREAD and ERASE through `0xd4c` and the second feeds the WRITE programs through `0xd48`. Evidence: [RE-35](14-evidence.md#14335-re-35-cpu-driver-timing-word).
- **Inferred.** The CPU does not reset the chips; the READID program does (its first command is `FFh`), and the initialisation function resets the sequencer, zeroes `FMC_CTRL0` and the register at `+0x400`, builds an identity chip-enable map of 8 words and runs the READID program. Evidence: [RE-36](14-evidence.md#14336-re-36-cpu-driver-chip-reset), [RE-37](14-evidence.md#14337-re-37-cpu-driver-initialisation).
- **Inferred.** The chip modes 1, 2, 3, 4, 8, 9, 12 and 13 select the write program (WRITE, WRITE_78, WRITE2P, WRITE2P_78 or WRITECACHE), the number of planes (the halfword 1, 2 or 4) and the two callbacks. Evidence: [RE-38](14-evidence.md#14338-re-38-cpu-driver-modes).
- **Inferred.** The driver's result classification: for a run result word, bits 7:0 are the per-page correction bits, bit 29 an erased page and bit 30 an uncorrectable page; the evaluator returns `0x80020000` for an uncorrectable page, 1 for a single erased page (bit 29, low byte 0), 0 otherwise and sets the level (1..8) to the highest correction bit; for a program or erase, bits 7:0 are the chip-enable mask, bit 27 is set by the fault tail when `C50` bit 0 is set, and bit 28 marks a status fail or a sequencer fault (the driver returns `0x80030000` when it is set). Evidence: [RE-13](14-evidence.md#14313-re-13-page-verdict-in-read), [RE-18](14-evidence.md#14318-re-18-page-word-and-fmc_status-b27), [RE-25](14-evidence.md#14325-re-25-fault-handlers), [RE-39](14-evidence.md#14339-re-39-cpu-driver-result-classification).
- **Inferred.** The driver never sets an ECC mode (the programs do) and runs no buffer-reset handshake (as the 4G and 5G drivers do), because it never accesses `0x814`, `0xc60` or `0xc64`; it never reads `CS_STATUS` or the PC. Evidence: [RE-40](14-evidence.md#14340-re-40-cpu-driver-other-sequencer-registers).
- **Inferred.** The second set of nine programs is a duplicate that the driver does not use, because no word of the image points to it; it sits in the restore image's update payload. Evidence: [RE-3](14-evidence.md#1433-re-3-program-locations-as-memory-addresses), [RE-41](14-evidence.md#14341-re-41-second-microcode-copy).
- **Inferred.** The strings place the driver in the Whimory 2.1 FIL layer for the M1A flash interface; the same text shows that the original firmware reports a sequence timeout. Evidence: [RE-42](14-evidence.md#14342-re-42-driver-generation).
- **Inferred.** The boot ROM reads a page without the sequencer, one controller per channel (stride `0x400`) and one sector at a time through the data buffers and the ECC engine, and its channel set-up switches the channel's pins to function 2; only channels 0 and 1 are handled. Evidence: [RE-43](14-evidence.md#14343-re-43-boot-rom-nand-access).
- **Inferred.** The original CPU driver does no cache maintenance in any function of the NAND driver, including those that load and start programs (the coprocessor-15 transfers in the image lie outside the driver). Evidence: [RE-44](14-evidence.md#14344-re-44-no-cache-maintenance-in-the-cpu-side-driver).
