# Chapter 16 — Device findings: risks and what only a device can settle

Summary: Risks that were identified for the engine and their status (section 16.1), and the results that only a device could settle, grouped by topic (section 16.2). The finding list with the evidence per finding is in [chapter 18](18-ledger.md).

## 16.1 Risks and their status

| # | item | what was at stake | status |
|---|---|---|---|
| 1 | Meaning of `wait` event 5 | an erase or program that polls on `wait` event 5 can end in a timeout fault too early, or wait without end | settled: the timeout (about 4.87 ms), `FMSS_C58` and the arming rule of `wait` event 5 ([chapter 16, section 16.2](#162-settled-on-a-device), [chapter 7, section 7.1](07-events-and-waits.md#71-wait-events)); the intermittent cases are open ([chapter 17, section 17.2](17-open-questions.md#172-events-and-the-status-latch)) |
| 2 | Sequencer instruction rate | delay loops in a program are sized from the time per instruction | settled: about 216 ns per instruction ([chapter 16, section 16.2](#162-settled-on-a-device)) |
| 3 | `FMC_STATUS` bit 27 semantics | the READ program's page word (its page result) depends on it | settled (device): set for every written sector, clear for erased ones ([RD7](11-nand-operations.md#1147-rd7-chunk-ecc-flag), [RD8](11-nand-operations.md#1148-rd8-page-result)) |
| 4 | Blank chunk decode result | an erased sector might decode as uncorrectable | settled (device): decoding an erased sector gives `ECC_RESULT = 0` |
| 5 | `FMC_CTRL0` bit 24, `FMC_DMA_CTRL = 7` placement | DMA stalls or truncates | the original programs set bit 24 around DMA and write `FMC_DMA_CTRL = 7` before the last DMA ([R7](11-nand-operations.md#1127-r7-dma-addressing)); `FMC_CTRL0` bit 24 enables DMA (device); the role of `FMC_DMA_CTRL` is open |
| 6 | Parity-buffer reuse between pages | corrupted metadata or parity | the original programs finish the metadata encode / decode of a page (the copy between the metadata registers and the slots) before the parity slot is reused ([RD6](11-nand-operations.md#1146-rd6-switching-chips), [WR3](11-nand-operations.md#1153-wr3-meta-encode)) |
| 7 | `pld` / `pst` (register-window load / store at an offset held in a register) outside `0xd60..0xd7c` | which addresses the indirect accesses can reach | settled: the offset wraps at 12 bits; they reach the whole register window including the sequencer registers r0..r7 ([chapter 16, section 16.2](#162-settled-on-a-device)) |
| 8 | Whether a run that contains only an `end` instruction, started after a reset, leaves flags set | waits in the next run pass early because of stale flags | the original prologue clears all flags at every start ([C2](11-nand-operations.md#1112-c2-prologue)); the run of only an `end` instruction after a reset is explained in [chapter 2, section 2.3](02-architecture.md#23-end-and-fault) |

## 16.2 Settled on a device

Small test programs were run on the sequencer of a unit. The CPU preset registers and parameter words, started the program, and read the register file, the PC and the control, NAND controller (FMC), ECC and parameter windows before and after, and sampled them while it ran. The chip enables were deselected throughout, except where a row says otherwise. Each result below was repeated in at least two runs, from a clean state (`C58`, `C4C` and `C5C` written 0 before each start).

### 16.2.1 Registers, instructions and fields

| topic | result |
|---|---|
| register file | r0..r7 are `0xc18 + 4n`; `SEQ_RESULT` (`0xc30`) is r6. A CPU write before the start is the register's starting value; a program start keeps the register values, a sequencer reset clears them |
| speed | about 216 ns per instruction (measured with a two-instruction loop: 873 us for 2 000 iterations, 8 657 us for 20 000) |
| instruction times | Each instruction was timed by executing it 100 x 10 times in a loop. Program in SDRAM: 217 ns per instruction for `movi`, `mov`, `add`, `0x08` (nop), a `bnz` not taken and a `wait` that passes; +37 ns for every access to the register window (`wr`/`st`/`ld`/`pld`/`pst`, NAND controller or parameter RAM alike); `ldi` +170 ns, `sti` +186 ns (RAM in SDRAM). The same programs from internal SRAM: 138 ns per instruction, window access +35 ns, `ldi` +218 ns, `sti` +120 ns. Instruction time is set by the fetch of the 8-byte instruction, not by the engine |
| ALU | `shr` is logical; a shift count of 32 or more gives 0 (immediate or register); `add`/`sub` wrap at 32 bits; an immediate of 0 selects the two-operand form (`r = r op rA`); `ld` ANDs the value read with its mask |
| memory | `ldi`/`sti`: little-endian 32-bit words; an unaligned address is rounded down to the word |
| `pld` / `pst` | the offset wraps at 12 bits (`0x1d64` reads `0xd64`); `pld 0xc18` returns r0 |
| parameter RAM | 32 words `0xd00..0xd7c` ([chapter 4, section 4.4](04-sequencer-memory-map.md#44-parameter-ram)) |
| field widths | `wr`/`st`/`ld` offsets `0x1d70`, `0x8d70`, `0xfd70` reached `0xd70`; branch targets and values written to r8 (the PC) with bit 12, 16 or 24 set went elsewhere, with bit 31 set landed on the target; `jr` (opcode `0x0f`) with any of those bits set did not jump |
| `end` fields | the `R` or `arg` field non-zero: the instruction faults instead of ending; the `imm` field is ignored; an END leaves its instruction word and `imm` in `0xc40` / `0xc44` |
| Fields left 0 | `imm` of `st`, `ldi`, `mov`, `sti`, `pld`, `pst`, `R` of `wr`, `arg` of `movi`: setting them to `0xff` or `4` had no effect |
| branches | `bz`/`bnz` ignore the argument field, test all 32 bits (`0x80000000` is non-zero), and take a target that is not a multiple of 8 as it is (a target 4 bytes after a label lands in the middle of an instruction, 8 bytes before it runs the instruction before the label) |
| `wait` fields | the argument and the immediate are ignored (register offsets with masks of set or clear bits made no difference); event numbers 16, 27 (event 11 plus 16), `0x8b` (event 11 plus 128) and 255 never passed: all 8 bits of the event number count, and a number above 15 does not act as its low bits |
| register numbers 8..255 | every number in every role ([`regsweep`](14-evidence.md#142149-regsweep-run-35); the table is in [chapter 4, section 4.3](04-sequencer-memory-map.md#43-register-file-r0r7-the-pc-and-register-numbers-above-7)): as a destination only 8 (jump) and 10 (all of r0..r7) act; in the argument (`arg`) field 9 and 11..255 read r0; `bnz` / `bz` with 8..255 never branch; `jr`, `ldi`, `pld` with 9..255 use r0 as the register or address; `st` with 8..255 stored the value the instruction just before it had written (0 after `movi r6, #0` in [`regnum`](14-evidence.md#14259-regnum-run-15), `0x5e075e5e` after `movi r7, #0x5e075e5e` in `regsweep`); no number reaches a control word Run 36 ([`stprev`](14-evidence.md#142156-stprev-run-36)): with the instruction before the `st` varied, `st` with 8..255 stored the last value that passed through the register file: the value the previous instruction wrote into a register, or the register value it read (r5 after `st [..], r5`, r0 after `nop` or `wr`); `wait` left it unchanged. |
| `r8`, `r10` | r8 is the PC: `movi r8, #label` and `mov r8, r1` jump to the label, `mov r1, r8` returns the offset of that instruction, and `ldi r1, [r8]` reads the bus address equal to that offset. A write to r10 goes to all eight registers (`movi`, `mov`, `add`). Register numbers 24 and 26 do nothing, so the whole field is decoded |
| writing the PC | the program's `wr [0xc38], #label` and `st [0xc38], r1` jumped to the label; `ld r2, [0xc38]` read the offset of that instruction |
| `0x0f` | **jump through a register**: `PC = r[arg]`, a byte offset from the program start (marker programs: arg 1 with r1 = label 1 landed on label 1; register field 1 with arg 0 landed on r0's label, so the target comes from the argument field; arg 9 and arg `0xd70` used r0; the immediate is ignored). The offset is not rounded: +4 lands in the middle of an instruction and the stream is decoded from there; -8 runs the instruction before the label. No return address is kept (r0..r7, `C3C`, `C48` unchanged), so a subroutine return is "load the return offset into a register, `0x0f` through it". Further cases fit: with RAM addresses in the registers the PC ended at that address + 8 and the fetched words were not program code; with r1 = `0xd70` it ran into zeroed memory and ended |

### 16.2.2 Opcodes

| topic | result |
|---|---|
| opcode map | all 256 opcodes, each in three operand forms (registers seeded with RAM pointers, `C58` = 0). The 19 opcodes used by the original programs (`0x00..0x07`, `0x0a..0x0e`, `0x11`, `0x13`, `0x14`, `0x17..0x19`) plus `0x08`, `0x0f`, `0x10`, `0x12`, `0x15` and `0xff` did not fault in the sweep. `0x09` (`wait2`) and `0x16` (`evjmp`) timed out there, because the sweep used no `wait2` condition 5 or 33 and no event was pending. No other opcode changed a register, RAM, parameter RAM or any window word. Every opcode `0x1a..0xfe`: stalls about 4.87 ms, then the timeout fault |
| `0x12` and its fields | stops the program in every form tried: register field 0, 3 or 11 (with the matching event set or not), argument 5, immediate `0x40`; so it is not a `wait` without a timeout. |
| `0x12` and CPU writes | none of the following CPU writes released it: `C48`, `C54`, `C3C`, `C5C`, `C58`, `C4C`, `C10`, `FMSS_CTRL` (`0x1`, `0x3`, `0x9`, `0x4`, `0x20001`), a CPU-sent `70h`, `FMC_STATUS` all ones, parameter RAM, r0, `C14`; `FMSS_CTRL` = `0x3` changed `C08` to 3 and `FMSS_CTRL` = `0x9` changed it to 0, without releasing the `pause`; `C58 = 0xff` set `C5C`. The CPU continues it by writing the PC (`0xc38`) and then a start word ([chapter 6](06-opcode-reference.md#12-pause)); otherwise the reset ends it |
| `pause` (opcode `12`) | the program stayed blocked for 2 ms; then CPU writes of the PC (`0xc38`) = the offset of the pause instruction + 8 and of a start word continued it (END 25 us later), with or without acknowledging `CS_IRQ` bit 3; acknowledge then start, start then acknowledge, and start twice left it paused |
| opcodes and pending flags | from a clean state, with nothing, one flag (command, DMA, ECC, status), all four, or one of the second register set's flags pending: `08`, `10`, `15`, `ff` behaved the same in every state; `12` blocked in every state; `16` went to the fault vector for every flag; `09` timed out in every state with event field 0 |
| `wait2` | condition 5 passed in every state of every run; condition 33 passed in every state of runs 29 to 34 (idle, during an erase, during an ECC operation and a DMA) and in no state of run 35 ([`evsweep2`](14-evidence.md#142137-evsweep2-run-35)); condition 20 passed in run 35 with every interrupt enable on and a command flag pending; every other N (0..255) never, also during a chip's erase, program or read, an ECC operation, a DMA and after a command to the second register set. With each flag of the second register set pending alone, `wait2` conditions 0 to 15 were tried and only condition 5 passed, while `wait` events 6, 7, 8 and 9 passed for the second set's command, address, DMA and transfer flags respectively Run 36 ([`w2state`](14-evidence.md#142151-w2state-run-36)): condition 20 passed only with a command flag pending and `0x044` bit 0 set; condition 33 passed in none of 34 states, the first program after a power cycle included. Run 38 ([`w2vic`](14-evidence.md#142171-w2vic-run-38)): `wait2` condition N follows raw interrupt line N (VIC0 0..31, VIC1 32..63) in 64 of 64 conditions in four states; the NAND controller raises line 20 and the ECC engine line 43. |
| check of the rules | seven combinations of the rules above (three timeouts in a row with `C58 = 0`: about 14.6 ms, `CS_IRQ` = 5, the program runs on to its END; a shift by 31; a `pld` of r6 through the window; four `0x15` instructions; a 100-iteration loop; a `wait` event 11 followed by a timeout and a `0x10` instruction, giving `CS_IRQ` = 7; a store and an unaligned load) gave the results the rules above give for them; `FMSS_C50` bit 0 was not set by a fault, although the original handlers suggest it would be |

|---|---|

| events and `FMC_STATUS` reads | a sequencer read of `FMC_STATUS` or `FMC_NSTAT` (once or twice) before the wait does **not** consume an event (status latch then `wait` event 5: passed in all four variants; `wait` event 0 after a read passed; `wait` event 3 timed out with and without a read). One `wait` event 3 with CE0 selected passed in one program and timed out in three other programs: unresolved |
| `wait` event 5 | a status read (`70h`, then `FMCTRL1` = `0xca`) during an erase: the wait passed about 155 us later and the status byte went from `0x81` to `0xc0`; idle: at once. | events after the power cycle | `wait` events are levels, not consumed flags (see [chapter 7, section 7.1](07-events-and-waits.md#71-wait-events)); `wait` events 6, 7 and 9 belong to the second register set; `wait` event 15 never passed with the interrupt enables clear |

| `C58` bit 1 | in run 8 an END ran the fault vector once when the CPU had written `C58 = 2` and then `C4C`; with `C4C` written by the program, no END was diverted, with or without a fault before it. In run 35 none of ten CPU write orders (`C58`, `C4C`, `C5C` in different orders and repeats, `C58` = 3 or 6) diverted an END ([`c58b1`](14-evidence.md#142136-c58b1-run-35)); `C58` = 3 set `C5C` at the END (bit 0). Condition open Run 36, with the job's clean-up off ([`c58b2`](14-evidence.md#142155-c58b2-run-36)): `C58` = 2 diverted no `end` in three runs in a row, whatever the order of the `C4C` write; `C58` = 6 diverted the first `end` once; `C58` = 3 diverted every `end` after the first. |

### 16.2.4 Start word, states and the window

| topic | result |
|---|---|
| start word | each bit alone with bit 0, on a 1 000-iteration loop: bits 2 and 4..15 and 17..31 change nothing (same time, same samples); bits 1, 3 or 16 keep the program from running (`FMSS_CTRL` bit 18 set, PC 0, no END within 50 ms), as do `0xfff7`, `0xfffd`, `0xffff`. Bits 0..15 read back (bit 0 cleared), bits 31:16 read 0 apart from bit 18. Without bit 0 nothing starts. The original CPU driver's start word `0xfff5` has every bit of 15:0 set except bits 1 and 3. Run 35 ([`startbits`](14-evidence.md#142132-startbits-run-35), [`startdiff`](14-evidence.md#142131-startdiff-run-35)): bits 4..31 except 16, flipped one at a time from `0xfff5`, changed nothing in program fetch from SDRAM and SRAM, 2000 `ldi` / `sti` / `pld`, `sig`, a DMA with an ECC encode or a vectored fault, except for the timeout length set by bits 8..15; `0xfff5` / `0xffb5` and `0xffd5` / `0xff95` gave the same results in twelve programs. The same loop ran in 497 us from SRAM and 811..828 us from SDRAM |
| start word bits 1, 3, 16 | **bit 1 = pause before the first instruction**: the program waits (`C08 = 3`, instruction 0 fetched into `0xc40`/`0xc44`, bit 18 set) and runs in full once the CPU writes the start word without bit 1 (`0x1` or `0xfff5`, 2 ms later: END 411 us after that write); writes of `0x2` keep it paused. **Bit 3** and **bit 16** put it in the post-reset state (instruction 0 fetched, not run; `C08 = 0`) until a start without them; repeating `0x9` or `0x8` does not step it, so there is no single-step. Bit 17 alone does not clear r0..r7. Bit 3 reads back 0, bit 1 reads back 1 |
| pause and abort while running | a start word with bit 1 set, written by the CPU 1 ms into a 20 000-iteration loop: the program froze at once (no sample after the write; `C08 = 3`) and, with `0xfff5` written 4 ms later, continued from the same point (END 4 ms late). Bit 3 or bit 16 written while running: the program stopped and, released 4 ms later, ran again from instruction 0 (END 5 ms after the release, the full run). A start word without these bits written while a program runs does nothing (no restart) |
| reset and start | after `FMSS_CTRL = 0x30000` the first START fetches instruction 0 into `0xc40`/`0xc44` and executes it only if it is `end` (an END-only program completes from any address); any other instruction waits with `FMSS_CTRL` bit 18 set, and a second START (any CPU write of `FMSS_CTRL` with bit 0 set) runs the program from instruction 0. Register accesses between the reset and the START make no difference; writes without bit 0 do not release it |
| `C08` | a state code ([chapter 8, section 8.1](08-sequencer-control-registers.md#81-sequencer-control-block)): read by the CPU 1 ms into each state: 1 running, 4 waiting (`wait` event 2) and 4 stalled (illegal opcode; `C14` counted down to `0xc0` in both), `0xa` blocked, 3 paused, 0 held by start-word bit 3 and after an END; 5 when the program read it itself (after starting a DMA, an ECC operation or a chip command, after `sig` and in a fault handler: always 5, [`c08self`](14-evidence.md#142140-c08self-run-35)) |
| `C50` | bit 0 is set while a command flag is pending and clear otherwise; a timeout or an illegal opcode does not change it, and a handler's write of 1 does not clear it ([`c50fault`](14-evidence.md#142138-c50fault-run-35)); bit 8 stayed clear after soft resets in run 35 Bit 6 was set after a second-set command (`wait` event 6 pending); bit 8 did not appear in 17 reads ([`c50b8`](14-evidence.md#142152-c50b8-run-36)). |
| CPU register masks | the value read back after a CPU write of all ones, of 0 and of `0xa5a5a5a5`, for every block of the window; the masks are listed in [chapter 3, section 3.3](03-cpu-memory-map.md#33-cpu-only-rules) |
| address decode (sequencer view) | `pld` of every word `0x000..0xffc`; the decode (offset bit 9 not decoded, the mirrors, the second register set, the `0x100` block) is described in [chapter 4, section 4.2](04-sequencer-memory-map.md#42-segments-and-mirrors-sequencer-view) |
| access matrix | every word `0x000..0xffc` (27 words that trigger an action when accessed were left out), CPU and sequencer writing all ones / zero, read by both: see [chapter 3, section 3.2](03-cpu-memory-map.md#32-memory-map-the-register-window) |
| block `0x100` | writable words (sequencer `pst`, read back at the `0x300` copy too): `0x1b8` 1 bit wide; `0x1bc..0x1c8`, `0x1d4`, `0x1d8` 32 bits (power-on value all ones); `0x1cc`, `0x1d0` 24 bits (power-on values `0x008060` and `0x3010d0`); the rest reads 0 and keeps nothing. Meaning open. `0x1cc` and `0x1d0` set to 0 or `0xffffff` did not change the time of a 2112-byte page transfer (220 us), so they are not NAND bus timing ([`finale`](14-evidence.md#142130-finale-run-34)) |
| `FMC_28` | a 9-bit value, writable. It advanced by exactly 128 over 128 iterations of a `pld`/`sti` loop, and rose by `0x7c` (124) per probe run whatever the program did (64 instructions of eleven kinds, sequencer reads of `FMC_28` included, made no difference). In programs that write the set-up word first it read 0 before and after 32 repetitions each of plain instructions, `sti`, `ldi`, parameter-RAM writes, DMAs (`0x2e0`), ECC encodes and 16-byte chip reads ([`finale`](14-evidence.md#142130-finale-run-34)): none of these advance it, and the set-up word (or something in it) clears it. It is the read position of the FIFO port (next sentence). In run 35 it did not change while a program ran, except that a DMA and the set-up word set it to 0; it advanced by 248 between the CPU's before-dump and the start and by 124 between the end and the after-dump ([`fmc28b`](14-evidence.md#142135-fmc28b-run-35)) It is the read position of the FIFO port: each read of `0x080` advanced it by 4, wrapping at 512 ([`bufport`](14-evidence.md#142154-bufport-run-36)). |
| interrupt line | VIC1 raw bit 22 stayed clear for an END, a fault, opcode `0x10`, a `0x12` stop and every start word, after a power cycle and after a soft reset alike. The NAND controller and ECC interrupt enables route flags into `CS_IRQ` bits 4 and 6 but not into that interrupt line; VIC0 line 20 was seen in some cases.
